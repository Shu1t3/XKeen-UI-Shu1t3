# Проверка целостности обновлений

Для сетевой установки бинарника или архива требуется SHA-256 из метаданных соответствующего опубликованного релиза, полученных напрямую с `https://api.github.com`. При отсутствии корректного хеша установка запрещена. Проверка выполняется до запуска загруженного файла, остановки работающего сервиса и замены установленного бинарника.

Для выбранного тега и имени файла должна существовать ровно одна завершённая загрузка (`state: uploaded`) с полем `digest` формата `sha256:<64 шестнадцатеричных символа>`. Черновик релиза, другой тег, дубликаты имени, незавершённая загрузка или некорректный digest приводят к отказу. Для архива проверяется хеш всего загруженного архива до распаковки.

Метаданные запрашиваются без перенаправлений и без прокси окружения. Shell-скрипты дополнительно отключают чтение конфигурации curl. Загрузка самого бинарника может проходить через прокси: полученные байты всё равно должны совпасть с доверенным хешем. Установщик `setup.sh` и скрипт перехода `scripts/switch-to-fork.sh` требуют `jq` и `sha256sum` для сетевой установки, включая выбор точного тега. При необходимости установите `jq` командой `opkg install jq`.

Встроенное обновление панели и ядер повторяет запрос метаданных при ошибках
соединения, таймаутах, обрыве ответа и HTTP 408/429/500/502/503/504. Выполняется
до пяти попыток с задержками 1, 2, 4 и 8 секунд; общий лимит получения метаданных —
три минуты. `Retry-After` (секунды или HTTP-дата) увеличивает задержку; HTTP 403
повторяется только при наличии корректного `Retry-After`. Если требуемая задержка
не укладывается в общий лимит, операция завершается без преждевременного повтора.
Причина сетевой ошибки и номер повтора записываются в журнал. Некорректные
метаданные, отсутствие SHA-256 и несовпадение хеша повтором не обходятся.
Эти повторы относятся к backend панели; поведение shell-установщиков не меняется.

Если GitHub API недоступен, исчерпан его лимит запросов либо автор релиза не предоставляет digest, установка завершается отказом. Повторите её после восстановления доступа или публикации корректных метаданных. Переключение на другой источник метаданных или отказ от проверки не выполняются автоматически.

SHA-256 обнаруживает изменение загружаемых байтов относительно метаданных GitHub. Это не цифровая подпись издателя и не независимая гарантия происхождения: доверие сохраняется к HTTPS, GitHub и аккаунту, публикующему релиз. Компрометация этих источников доверия выходит за пределы этой проверки. Хеш также не подтверждает работоспособность программы; проверки архитектуры, версии, конфигурации и запуска выполняются отдельно.

## Явная локальная установка

Обычный setup.sh больше не обнаруживает автоматически бинарник в `/opt/tmp`.
Для доверенной локальной сборки администратор явно запускает `sh setup.sh --local`:
тогда используется `/opt/tmp/xkeen-ui-<архитектура>`. В скрипте перехода локальное
доверие явно задаётся `--file <путь>` или `--rollback <каталог резервной копии>`.
Эти ручные режимы не требуют GitHub-хеша и не подтверждают происхождение файла;
администратор отвечает за источник. Проверка запуска и архитектуры сохраняется
в соответствующих установщиках. Переход в ручной режим при сетевой ошибке
никогда не выполняется автоматически.

После публикации CI сверяет SHA-256 всех трёх бинарников с полем digest GitHub.
Подписанный manifest не используется по согласованному выбору источника доверия.
